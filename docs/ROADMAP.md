### 出站代理（本轮实现）

**为什么是当前最该做的一项**：上游按出口 IP 限流与封禁。所有账号共用服务器
那一个 IP 时，几十个号的流量会叠在一起，很容易被判定成异常流量，
表现为"偶发 429/403" —— 排查时又极易误判成凭据或倍率问题。

实现要点：

- `proxies` 表：`name / protocol(socks5|http|https) / host / port / username / password_enc / fallback / enabled`
- `accounts.proxy_id` 绑定；**每账号可选**，NULL = 直连
- 网关按账号取客户端（`GatewayState::client_for`），按 `protocol://host:port` 缓存连接池
- **回退策略默认 `fail`**：代理挂了直接失败，不静默直连 ——
  用户绑代理通常就是为了隐藏真实 IP，静默回退会把它暴露出去
- 代理密码由**网关加密**（主密钥只在网关进程里），Go 只存密文

踩过的坑：`&String` 绑定到 `jsonb` 列会被 sqlx 推断成 `text`，
写入直接报错；而错误被 `let _ =` 吞掉，表现成"功能打开了却没有数据"。
必须显式写 `$2::jsonb`，且**失败要打日志**。

### Prompt 留存（本轮实现）

`usage_payloads` 表，与 `usage_logs` 一对一（`ON DELETE CASCADE`）。

- **默认关闭**（`payload.enabled = false`）：留存的是用户完整对话内容
- 保留天数独立（`payload.retention_days`，默认 7 天）
- 只存语义内容（messages / system / tools / 最终文本），**不存原始 HTTP 体**
  （那里面有客户端 header，可能含认证信息）
- 单条上限 256 KiB，超出截断并显式标记

### 仪表盘错误分布 + 延迟分位（本轮实现）

- **错误分布**：按 `error_detail` 的类型前缀分组，最多 8 类，带占比条与样例。
  成功率只说"有问题"，错误分布才说"问题在哪"。
- **延迟分位**：P50/P95/P99（`percentile_cont`，PG 侧算）。
  平均值会被长尾拉偏 —— 99 个快请求 + 1 个超时，平均看起来正常，
  但用户感受到的是那 1 个卡死。

### 定价与计费（本轮打通）

**曾经的真实状态**：`upstream_cost` / `billed_cost` 在网关侧**硬编码 `0.0`**，
价格从未参与过任何计算。库里那些非零成本全部来自迁移导入的历史数据 ——
也就是说"计费"从来没生效过。

现在的链路：

```
models 表（价格） → /internal/prices → 网关 PriceBook（内存） → 计费 → usage_logs
```

**三条计价规则**：

| 项 | 算法 |
| --- | --- |
| 上游成本 | `(非缓存输入 × 输入价 + 缓存 × 缓存价 + 输出 × 输出价) / 1e6` |
| 记账额度 | `上游成本 × 模型倍率 × 渠道倍率` |
| 缺失价格 | 成本记 0 并**不报错**：用户要的是回复，不是账单 |

**缓存必须单独计价**：它通常只有输入价的 1/10，而长对话里缓存能占输入的 80% 以上。
合成一个"输入价"会把成本算高好几倍。

**三个价格来源**（页面顶部都有入口）：

1. **内置价格表**（`store/builtin_prices.go` 的 `BuiltinPrices`）：104 个模型 ID 的官方参考报价，
   保留美元/人民币币种、来源与档位，由“内置价格填充”按钮触发。**只填三项单价均为 0 的模型**——
   人工改过的价格可能是谈下来的折扣价，被同步改回标价会直接影响毛利。
   2026-10-29 核对的来源与限制见 [内置模型价格说明](builtin-model-prices.md)。
2. **OpenRouter 实时拉取**：实测拉到 **467 个模型**，更新了本地 13 个。
   它没有国内自建模型，所以是补充而非替代。
3. **手工逐个改**：`PATCH /models/{name}`。

**踩过的坑**：

- `PATCH /models` 改了价格但**没推给网关** —— 网关用旧价继续记账，
  不报错、只让账单慢慢偏掉。已在 `pushPrices` 里统一挂到 `notifyReload`。
- 网关的目录里 `channelId` 实际是**平台名**（`workbuddy`），不是渠道 id（`wb-cn`）——
  平台下沉后的遗留。直接用它会导致所有模型显示"未分配到渠道"。
  现在用 `accounts` 表做一次「平台 → 渠道」反查。

### 分组级模型白名单（本轮实现）

管理员可以配置**每个分组对外提供哪些模型**。比如 WorkBuddy 分组只开放
`deepseek-v4-pro` 与 `glm-5.1`，其余即使账号能跑也不出现在模型广场里。

`channels.model_allow TEXT[]`：

- **NULL / 空 = 不限制**（该分组下能跑的模型全部对外）。
  与"空 = 一个都不给"相反 —— 后者会让新建分组默认不可用，且很难看出是"没配"还是"配成空"。
- 有值时只放行列内的（按**对外模型名**匹配，不是上游名）。

**关键实现点：必须叠加"网关目录里真的有这个模型"这一层。**

第一版只判断白名单，结果限制完全失效 —— 因为一个**没配**白名单的分组会
"放行全部模型"，于是任何模型都被它'提供'，限制别的分组就等于没限制。
实测：把 `wb-cn` 限制成 2 个模型后，公开清单仍是 21 个。

正确逻辑：模型可见 ⟺ 存在一个分组同时满足
① 网关目录里有这条路有（`ModelRouteSource`）；② 白名单放行。
修正后同一操作让清单从 21 降到 **4**（2 个开放 + fake 自带的 2 个）。

已锁（`model_visibility_test.go`，5 个用例）：
白名单为空放行全部 / 有值时只放行列内 / 停用分组不放行 /
只挂在受限分组下的模型不可见 / 价格取提供者里最低倍率。

**界面上的区分**：
- 管理员的模型广场会多一个「未对外开放」分组 —— 这是排查依据
  （"我配了白名单，结果它消失了"）；
- 普通用户看不到这一组，只能看到真正可用的模型。

**顺带修的一个 bug**：网关目录里的 `channelId` 是**平台名**（`workbuddy`），
不是分组 id（`wb-cn`）—— 平台下沉后的遗留。不做「平台 → 分组」反查的话，
所有模型都会被标成"未对外开放"。


「渠道」这个词已经名不副实：它的实际语义是**计价分组**（倍率、优先级、权重），
平台在账号上。继续叫"渠道"会和"上游渠道"混淆，所以：

| 旧 | 新 |
| --- | --- |
| 渠道与账号（导航组） | 分组与账号 |
| 渠道管理 | 分组管理 |
| 渠道状态 | 分组状态 |

API 路径（`/channels`）与数据库表名保持不变 —— 改它们要动迁移与所有调用方，
收益只是"名字更整齐"，不值得。

### 能力标签用中文 + 图标

不直接显示 `tools` / `vision` / `reasoning` 这些**字段名**：

| 字段 | 展示 |
| --- | --- |
| `tools` | 🔧 工具调用 |
| `vision` | 👁 视觉 |
| `reasoning` | ⑂ 推理 |

字段名是给代码看的；一屏十几个英文单词，扫视成本远高于图标。

### 能力来源分三档，不是"未知 / 已知"

`capabilitiesKnown` 这个布尔被拆掉了，因为它同时被当成两件事用，两头都不对：

| 值 | 含义 | 界面 | 调度 |
| --- | --- | --- | --- |
| `live` | 上游实时目录带着能力位 | 只显示能力标签 | 参与硬过滤 |
| `snapshot` | 我们按厂商文档维护的内置对照表 | 标签 + 「按内置对照表」 | **参与硬过滤** |
| `none` | 上游没说、我们也没有对照记录 | 只显示「能力未知」 | 乐观放行，让上游报错 |

改之前的两个具体故障：

1. 卡片上出现「工具调用 视觉 推理」和「能力未知」**并列** —— 用户以为系统坏了。
   实际是"有值，但值的来源是我们自己的对照表"，那不该叫"未知"。
2. 快照条目的能力位在调度里**完全不参与过滤**，那份对照表白维护。
   现在 `snapshot` 与 `live` 同等参与 `reject_reason`，只有 `none` 才放行。

注意 `snapshot` 仍然可能比上游实际能力旧 —— 所以界面说的是
「按内置对照表」而不是「官方支持」，把判断的来源讲清楚。

### 价格以官方牌价为准，管理员手工维护

**OpenRouter 拉下来的价格不准**（它自己的加价、缓存价缺失、部分模型标价离谱），
按它计费会让账单莫名其妙。调整为：

| 来源 | 定位 |
| --- | --- |
| **内置价格表** | 按官方定价页维护，点击填充仅更新三项单价均为零的模型；目录同步不改价 |
| OpenRouter | **降级为参考**，管理员可手动触发，但需自己复核 |
| **管理员手工编辑** | **最终以它为准** |

价格编辑对话框（`ModelPriceDialog`）：
- 输入价 / 输出价 / 缓存读取价 / 模型倍率 / 是否对外启用；
- 单位是**元 / 百万 token**，与展示一致，不做隐式换算；
- **只有管理员能打开** —— 普通用户拿到的 `onEditPrice` 是 `undefined`，
  连按钮都不渲染（不是"渲染了但禁用"）；
- 保存后自动推给网关，**下一条请求即按新价计费**。

实测：把 `fake-model` 改成 100/300/10 后发一次请求，
落库 `upstream_cost = 0.00275000`，与手算
`(11-5)×100 + 5×10 + 7×300 = 2750 ÷ 1e6` 完全一致。

### 结算：把"消费了不扣钱"补上（本轮最大修复）

**真实状态**：网关算出 `billed_cost` 并写进 `usage_logs`，但**从来没有扣过用户余额**。
用量、账单、价格全对，只有"扣钱"这一环是空的。

两个根因叠在一起：

1. **网关从不碰 `users.balance`** —— 它的存储层连 `users` 表都不读；
2. **`api_keys.user_id` 从来没写过** —— 所有 Key 归属都是 NULL，
   于是即使有结算逻辑也找不到该扣谁。

修法：

- `POST /keys` 写入当前登录用户的 `user_id`（`nullableUserID` 把 0 存成 NULL，
  因为 0 不是合法用户，直接写会违反外键）；
- `usage_logs.settled_at`（迁移 015）+ **部分索引**
  （只索引未结算行 —— 绝大多数行已结算，全表索引是浪费）；
- `Store.SettleUsage`：挑未结算 → 按用户汇总 → 一个事务里扣余额 + 写流水 + 标记已结算；
- **幂等**：靠 `settled_at`，定时任务与手动触发同时跑也只扣一次；
- 后端每分钟自动结算一次（不能靠"管理员想起来点一下"，那会让余额长期是旧值）。

**余额不足不扣成负数**，但用量仍然标记已结算 ——
否则这批数据会被反复挑出来、无限重试刷日志。这类用户单独返回给管理员。

实测：余额 `100.000000` → `99.986239`，扣款 `0.01376064` 与返回金额一致；
第二次结算 `count=0`（幂等生效）；流水正确记为 `kind='usage'`。

### API Key 的模型白名单按分组收窄

`KeyFormDialog` 里 `availableModels` 的两个分支**都 `return models`**（全量），
注释写着"选了渠道后只能勾选该渠道提供的模型"却完全没实现 ——
于是白名单里能看到这个分组根本不提供的模型，选完调过去必然 403。

现在按 `/catalog/models` 的 `channels[].exposed` 过滤：
只显示所选分组**真正对外提供**的模型。分组一个模型都没有时也显示空，
让人看出问题而不是给一堆选不了的选项。

### API Key 的用量与消费

Key 列表新增两列：**用量**（累计 token / 今日 token）与 **消费**
（累计金额 / 今日金额），单位元，取 `billed_cost`（记账额度，含倍率）。

独立查询 `ListKeyUsage`（一次 GROUP BY），不塞进 `ListKeys` ——
用量要扫整张 `usage_logs`，塞进列表查询会让"打开密钥管理"变成全表扫描。
查询失败时省略该字段、显示 0，不阻断密钥列表。

### 显示名称改为自动获取

OAuth 平台（WorkBuddy / Trae）授权完成后，网关拿 token 问上游「这个号是谁」，
把返回的昵称或邮箱写进 `accounts.nickname`。所以**表单里不再显示这一项** ——
显示一个"不需要你填"的说明只是多一行噪音。

只在自定义供应商时保留（那种拿不到上游身份，必须自己起名）。

### 授权完成后自动检测

不再有「检查授权状态」按钮。用户在上游点完"允许"不会回到弹窗操作，
让他自己点一下去"确认系统有没有收到"，是把系统该做的事推给人。

改成 2 秒一次的自动轮询：成功后**直接关窗 + 刷新列表**，
期间显示"在上游页面完成授权即可，这里会自动检测"。
`needsCallback` 的平台（要贴回调地址）没法自动，保持手动。

### 空分组不再报「渠道不存在」

`adapter_for_channel` 原先只从「该分组下的第一个账号」推断适配器，
账号为空就返回 `None`，接口报「渠道不存在」—— 但分组明明在，
把人引向"网关是不是挂了"这个错误方向。

现在加了 `channel_platforms`（分组 → 平台）兜底：
适配器与账号无关（账号只是凭据），空分组也能看到任务与能力，只是没有号可跑。

### 内置平台无条件注册

**真实故障**：管理员把分组全删掉之后，「新建账号 → 开始授权」报
「平台 workbuddy 不可用」。因为适配器注册表只从 `channels.adapter` 推导 ——
表空 → 注册表空 → 连登录都迈不出第一步。

改成 `BUILTIN_PLATFORMS` 无条件注册（`fake` / `workbuddy` / `custom` / `trae`）。
**登录授权不该依赖"已经有账号/渠道"。** 已用测试锁死。

### 新建分组不配置对外模型

新分组里一个账号都没有，网关也就没有它的模型目录 ——
这时候能选的模型要么是空的、要么是全站的（没有依据）。

改成本地只在**编辑已有分组**时显示「对外模型」，
新建时给一句提示：保存后先加账号，网关拉到目录后再回来配。


分组名下账号全停用（或缺凭据）时，网关不会拉它的模型目录 ——
所以该分组一个模型都没有。这不是 bug，但**界面必须说明**，
否则管理员会以为分组丢了。

现在：管理员的模型广场会列出**所有分组**（包括 0 个模型的），
并标注「该分组名下没有启用的账号，网关不会拉它的模型目录」。
筛选按钮也来自分组表而不是从模型反推 —— 否则空分组连筛选里都看不到。


`GET /api/v1/public/models`（**无需鉴权**）+ 两个入口：

- `/models` —— **在应用外壳内**，带侧边栏，给已登录用户；
- `/plaza` —— 在外壳之外，给未登录访客。

目的：让人**在决定用不用之前**就能看到"有哪些模型、多长上下文、多少钱"。

### 模型目录同步（重要修正）

**曾经做错**：模型广场读 `models` 表，而那张表从来没有数据 ——
模型清单只存在于**网关的内存矩阵**里（从各渠道适配器实时拉取），
从不落库。所以我之前塞了 3 条假数据，那是掩盖问题而不是解决问题。

现在的链路：

```
渠道适配器 → 网关矩阵（内存）→ /internal/catalog → 管理面 SyncCatalog → models 表 → 页面
```

- 启动后 **30 秒**首次同步（网关要先建矩阵），之后**每小时**一次；
- 也可手动 `POST /api/v1/catalog/sync`；
- 同步**只更新目录字段**（上下文、能力、最大输出），
  价格、倍率、启用状态保持人工配置 —— 那些是人的决定；
- 网关返回空清单时**跳过清理**：那通常意味着网关刚重启、矩阵还没建好，
  此时清空整张表会让用户以为模型全没了。

实测：同步到 20 个真实模型（deepseek / glm / kimi / hy 等），能力字段齐全。
价格全是 0，因为从没配置过 —— 页面显示「未定价」，这是真实状态。

### 运维监控页（本轮补齐）

`/ops`，数据来自 `GET /api/v1/ops/overview?windowMinutes=&bucketMinutes=`。

与仪表盘分工：仪表盘回答"用了多少、好不好用"，运维回答"现在能不能扛住、哪里在漏"。

**指标一律画成图**。TTFT / OTPS / 吞吐都是随时间波动的量，
一串数字只能说明"此刻是多少"，看不出"是不是刚变差"。
排障要看拐点，不是瞬时值。四个图：

| 图 | 内容 | 为什么 |
| --- | --- | --- |
| **延迟分位** | 首字 P50/P95 + 总耗时 P50/P95，同轴四条线 | 曲线整体抬高 = 上游变慢 |
| **输出速度 OTPS** | P50/P95（tok/s） | 吐字速度掉下来，用户立刻能感觉到"卡" |
| **请求结果** | 成功/失败堆叠 | 失败柱变高时对照延迟曲线找关联 |
| **Token 吞吐** | 输入/输出堆叠 | 看清是"请求多"还是"单次 token 多" |

运行态用横向**堆叠条**（并发水位、账号健康）—— 那是唯一适合"填满"语义的表达，
其余一律曲线。

只有三种情况用纯文字，因为图表达不了：告警原文、网关离线原因、空态提示。

**OTPS 口径与使用记录的速度列完全一致**，否则同一份数据在两张页面上
给出不同数字，用户不知道信哪个：

- 有 `ttft_ms`：`completion / ((total - ttft) / 1000)`，要求 completion ≥ 100
- 无 `ttft_ms`：`completion / (total / 1000)`，要求 completion ≥ 200

`null` 全部换成 `undefined` 传给图表：Recharts 的 `monotone` 遇到 null 会断线，
而"该时段没有样本"和"该时段值为 0"是两件不同的事，不能都当 0。

网关离线时返回 **200 + `gatewayOnline: false`**，不是 500 ——
"网关挂了"本身就是最重要的运维信息，报 500 会让页面白屏、看不到原因。
性能指标**独立于网关状态**先查：它只依赖已落库的历史数据，
而"网关刚重启"正是最需要看趋势的时候。

## 二、第一档：强烈建议做（直接影响日常可用性）

### 1. 出站代理管理（Proxies）

**sub2api**：2087 行，代理池 + 每账号绑定 + 回退策略（`none` / `proxy` / `direct`）。

**为什么需要**：上游按 IP 限流与封禁。同一出口 IP 打几十个账号，很容易被判定为异常流量。
现在我们所有账号共用服务器出口 IP —— 这是**当前最大的稳定性风险**。

**做什么**：
- 代理表：`name / protocol(socks5|http) / address / auth`
- 账号绑定代理（`accounts.proxy_id`）
- 回退策略：代理挂了时 `direct` 还是 `fail`
- 网关侧按账号选 `reqwest::Proxy`

**成本**：中（网关要改 transport 层 + 迁移 + 页面）。

### 2. 账户余额 / 订阅到期提醒

**sub2api**：`Subscriptions`（1644 行）+ 到期前邮件/站内提醒。

**为什么需要**：上游账号会到期、余额会耗尽。现在只有"失败了才知道"，
而探活只能发现"已经不可用"，发现不了"3 天后到期"。

**做什么**：
- 账号加 `expires_at`（已有）与"低额度阈值"
- 巡检时检查，触发 `notify`（webhook 已有）
- 页面上一眼能看到"哪些号快到期/快没额度"

**成本**：低（复用现有探活与通知链路）。**性价比最高的一项。**

### 3. 请求级 Prompt / 响应内容留存（可选开关）

**sub2api**：`PromptAudit`。

**为什么需要**：出问题时无法复现。现在 `usage_logs` 只有元数据，
看不到"用户到底发了什么、模型回了什么"。

**注意**：这是隐私敏感功能，必须
① 默认关闭；② 打开时明确提示；③ 可配置保留天数与脱敏规则。

**成本**：低-中（新表 + 开关 + 清理）。**建议做成默认关闭的实验功能。**

## 六、还需要补齐的"欠账"

这些不是新功能，是现有实现的缺口：

1. **多账号串行执行的端到端验收**：目前只有 `wb-cn` 一个号有真实凭据，
   "3 个账号串行跑完"还没在真实上游验证过。
2. **WorkBuddy / Trae 适配器的真实登录**：登录流程代码已就绪，
   但真实 OAuth 只在文档层面推演过，没有跑通一次完整授权。
3. **网关热重载**：现在改渠道/账号后靠 `notifyReload`，
   大量变更时可能漏；需要一次"全量重建"的兜底入口。

### 任务菜单消失：`adapter` 被硬编码成 `custom`

**症状**：左侧「任务」整组不见了，`/tasks/wb-cn` 打开是「渠道不存在」。

**根因**：新建分组时 `ChannelFormSheet` 把 `adapter` 硬编码成 `"custom"`，
注释还写着「渠道不再绑定平台，传 custom 只是为了满足旧接口字段要求」。
**这个假设是错的**：

- `adapter` 决定用哪套上游协议（`workbuddy` / `custom` / `trae` / `fake`）；
- 它同时决定运营能力 —— 任务、签到、每日动作都由适配器声明；
- `custom` 适配器不声明任何能力，于是 `channel_caps.tasks = false`，
  后端 `listTaskChannels` 返回空，菜单整组消失（不报错，只是没有）。

现在表单让用户选平台与版本（WorkBuddy 国内 / 国际、自定义供应商），
`adapter` 与 `options.realm` 跟着走。

### 国内版与国际版必须分开建分组

`realm` 是**账号级**属性（`accounts.options.realm`），但**路由层完全不看它** ——
只按分组 / 模型 / 可用性筛候选账号。所以：

- 国内号打 `copilot.tencent.com`，国际号打 `workbuddy.ai`，**上游域名不同**；
- 混在一个分组里，路由会把请求发给"另一个区"的号；
- 该号 `realm` 没填时默认按 `cn` 处理，于是打到错误域名，表现为 **401 / 404**。

代码注释里本来就写着「国内号与国际号共用一份 hosts，其中一类必然打到错误域名」。
**结论：必须分成两个分组。** 这是当前架构决定的，不是配置问题。

能力差异也随之落在分组上：

| 能力 | 国内版 | 国际版 |
| --- | --- | --- |
| 任务 | ✅ | ❌ |
| 每日签到 | ✅ | ❌（改为每日对话） |
| 猫猫旅行 | ✅ | ❌ |

### 补上 `WorkBuddy_Valorant` 任务

对照参考实现（`workbuddy2api-hub`）逐条比对任务码，发现缺这一个：
它要求召唤**特定专家** `ex_xQHHD1u5Jkua`（无畏契约拼豆专家），
用静态专家池里的 id 不会推进进度。已单独走固定 id 分支。

其余 24 个任务码的 `kind` 与参考实现逐字一致，无需改动。

### 定时探活：设置项存在，但从来没人执行

**症状**：设置页里「定时探活」是开着的，用户以为有人盯着账号，
其实**没有任何代码去跑它** —— 只有手动点「探活」才真的打一次上游。
凭据过期、被封、额度耗尽，都要等真实用户请求失败才发现。

**实现**（`handler/probe_scheduler.go`）：

- 对每个**启用**的账号发一句 hello；停用账号跳过（不参与调度，探它纯属烧额度）；
- **串行 + 每条间隔 1.5 秒**：并发打过去会让上游看到一阵脉冲，更容易被判成异常流量；
- 单账号失败**不中断整轮**：一个号挂了不该让剩下的号这轮都跳过；
- **结果只记日志，不写 `usage_logs`**：探活真的会消耗 token，
  混进用量表会污染账单与统计；账号可用性由网关冷却状态反映；
- **间隔每轮重新读设置**：改完下一轮就生效，不用重启进程；
- **手动与定时走同一个函数**（`RunProbeSweepExclusive`），并用互斥锁保证
  不会同时跑两轮（两个路径分叉的话，行为会慢慢变得不一致）。

同时新增 `POST /accounts/probe-all`，一次性对所有启用账号跑一轮并返回统计。

实测：启动 45 秒后首轮完成，「2 个账号，成功 2，失败 0」；
手动接口返回 `{"total":2,"ok":2,"failed":0}`。

### settings 表里的 0 会盖住默认值

`settings` 存的是**覆盖值**：只要存过一个 0，它就一直盖住 Go 里的默认值，
哪怕后来把默认值改得更合理。

实测到的三个脏值（迁移 017 修正）：

| key | 原值 | 后果 |
| --- | --- | --- |
| `probe.interval_minutes` | 0 | 间隔非法，与"最短 5 分钟"的提示自相矛盾 |
| `pricing.usd_to_cny` | 0 | 汇率缺失 → **所有美元价折算成 0，模型全变免费** |
| `payload.retention_days` | 0 | 留存 0 天 = 永远不存 |

迁移只修**业务上不成立**的值（0 / 负数），不动用户设过的有效值 ——
"和默认值不同"不是修它的理由。

`probe.enabled` 是合法选择（有人就是不想烧额度），默认值改为开启，
但老库里如果关着，这个迁移**不会**强行打开。

### 探活模型：展示 + 可指定

**问题**：探活一直按「免费优先」自动挑模型，但界面上**看不到用的是哪个**，
也不能改。这留下一个盲区 —— **免费模型通了不代表真实模型能通**：

- 分组只挂了推理模型，免费档是另一个轻量模型 → 探针一直绿，真实请求却因无权限失败；
- 某个号被单独限权，只有特定模型可用。

**做法**：

- 网关 `probe_account` 接受 `?model=` 查询参数；不传仍按免费优先（默认行为不变）；
- `channels.probe_model`（迁移 018）存**对外模型名**；空 = 自动；
- 分组状态卡显示「探活模型」，未指定时显示「自动（免费优先）」而不是留空 ——
  留空会被读成"没有探活"；
- 卡片上的铅笔按钮打开对话框，**只列出该分组真的对外提供**的模型：
  列全量会让人选到分组根本没有的模型，探活必然失败，而那是配置错误不是账号故障，
  会误导排查方向。

实测：设置 `workbuddy` 为 `glm-5.1` 后，数据库与健康接口都正确返回，
定时探活下一轮即用该模型。

### 上游渠道校验误拦：DSH 路径声明的连续文本

**症状**：所有请求返回

```
400 {"message":"upstream 400: ... Illegal API invocation from an unapproved channel ..."}
```

错误分类本身是对的（`ChannelBlocked`，可重试），但**根因没消除** —— 换号重试仍然被拦。

**根因**：上游校验的是「连续文本」。DSH 的系统提示里这两句紧挨着出现：

```
Tokens prefixed with @ are paths the user explicitly referenced.
Relative paths resolve from the workspace root; absolute paths identify files or directories on the host.
```

A/B 结论：**单句各自 200，连排必 400**；改第二句无效，改**第一句**才解除匹配。

**修复**（`hygiene.rs`）：

- 新增 `DSH_PATH_PREFIX` 字面量 + `dsh_path_regex()`；
- 在第一句的 `are paths` 后插入 `that`，句意不变，但连续文本已不匹配签名；
- `has_fingerprint_with` 里加**字面量快速路径**（先 `contains` 再跑正则）——
  多数请求不带这句，不该为它付正则的代价；
- 只在 `identity`（system / developer）分支生效：user 内容是用户数据，
  改了会与磁盘不一致。

**为什么用捕获组而不是 look-ahead**：`regex` crate 不支持 lookaround。
参考实现按 look-ahead 写，这里用捕获组回填，效果等价。

实测：带这两句的请求连续 3 次全部 200（修复前必 400）。

### 数据层迁移：pgx 手写 SQL → GORM

**范围**：后端全部（迁移机制 + 查询层）。

| 项 | 迁移前 | 迁移后 |
| --- | --- | --- |
| 迁移 | 18 个手写 SQL 文件 + 自研执行器 | `AutoMigrate` + 显式迁移表 |
| 模型 | 无（SQL 里内联） | `internal/models`，16 张表 |
| 查询 | `pgxpool.Query/QueryRow/Exec` | GORM `Raw/Exec/Transaction` |
| 驱动 | `pgx/v5` 直连 | `gorm.io/driver/postgres` |

**旧 SQL 文件已备份**：`backend/artifacts/migrations-legacy/`（18 个）。

**Schema 对拍**：177 个列定义，与旧库**逐个一致**。

踩过的坑（都已修，且写了测试或注释）：

1. **`int` 被映射成 `bigint`**：GORM 默认把 Go `int` 当 `bigint`。
   显式 `type:integer` 才对得上原表。
2. **`text[]` 扫不进 `[]string`**：GORM 无内置数组类型，
   自定义 `models.TextArray`（实现 `Valuer` / `Scanner` / `GormDBDataType`）。
3. **`Row().Scan` 与 `Scan` 语义不同**：
   前者要求"每个参数对应一列"，传结构体会报 `expected N destination arguments`；
   后者零行不报错，无法区分"查不到"。`queryOne` 按类型分流。
4. **`= ANY(?)` 被展开成 `ANY($1,$2,$3)`**：GORM 会展开切片参数，改用 `IN (?)`。
5. **唯一约束改名失败**：老库叫 `users_email_key`，GORM 认成 `uni_users_email`，
   每次迁移都 `DROP CONSTRAINT` 一条不存在的约束（SQLSTATE 42704）。
   按 SQLSTATE 识别并放行，注释里写清了原因。
6. **`text[]` 为 NULL 时前端崩页**：`/keys` 读 `arr[0]` 直接白屏。
   仓储层统一 `orEmptyText`，对外永远给空切片。

**测试**：
- `internal/database/migrate_test.go`：空库建表 + 幂等（用独立库 `TEST_DATABASE_URL_MIGRATE`）
- `internal/store/store_integration_test.go`：分组 CRUD、**小数精度回归**、用户余额与扣款上限
